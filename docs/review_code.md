Reviewer: fresh code reviewer, no implementation history. Scope: everything under `src/project_planner/` (engine, persistence, services, facade, notebook) at commit `2b90b4c` (branch `backend0`), checked against `docs/contracts.md`, `docs/api.md`, `docs/decisions.md` and `docs/performance.md`. No product code or tests were changed.

Tooling run once: `ruff check src tests` is clean, `mypy` is clean (34 source files), and `pytest -q` gives 1042 passed, 4 deselected (perf) in 29 s.

Every finding marked "Confirmed" was reproduced with a scratch script run through `.venv\Scripts\python`. The repro is given in the table or in the notes under it.

## 1. Summary and overall assessment

The engine is in good shape. The forward-pass formulas (FS/SS/FF/SF with lag) are correct. Lag and duration rounding uses `ROUND_CEILING` on an exact `as_integer_ratio`, which never places a successor early. Effort sizing takes an exact `Fraction` ceiling. Day-boundary display (`start` vs `finish` convention) is consistent. Leveling has a clear termination argument: candidates only move forward, and the last load step is always 0. It keeps dependency constraints because each task's bound is at least its dependency-only start and at least every placed predecessor's constraint. The rollup, the loading sweep-line and the CSV round trip held up in every experiment I ran. Tie-breaks are deterministic everywhere I looked: sets are always sorted before they reach outputs or fingerprints.

The weaker areas are around the engine:

- **Data integrity across connections.** A `Workspace` assumes it is the only writer of its database file, but nothing enforces that. Two workspaces opened on the same file silently diverge and can corrupt the WBS (finding 1).
- **Persistence identity.** Saved-project IDs are reusable (finding 2), and `ProjectInfo` objects cannot be passed to `load` / `delete_project` even though the signatures say they can (finding 3).
- **Decimal context.** Money and day arithmetic outside sizing depends on the caller's ambient `decimal` context (finding 4).
- **Stale detection.** The schedule fingerprint includes resource IDs, so harmless resource edits mark dates stale and invalidate a pending leveling preview (finding 5).
- **Config not honoured.** `Config` is only partly applied: CSV import/export and all display rounding use `DEFAULT_CONFIG` (finding 6).
- **Efficiency.** The cost the user actually waits for after an edit is much larger than the 43 ms in `docs/performance.md`. After an edit, the first read spends about 190 ms recomputing fingerprints at 10k tasks. A rate edit with three stored runs takes about 3 s (findings 7 and 8).

None of the issues found affects the core scheduling arithmetic. **Overall: sound engine, ready after the High and Medium items are addressed.** Findings 1–6 are the ones I would fix before release.

Additional assessment (requested): **`pp.hours()` / `pp.days()` accepting floats through `Decimal(repr(x))`.** This is exact for literals: `pp.days(-0.5)` gives `-0.5d`. A computed float carries its binary noise into what is "stored exactly as entered": `pp.days(0.1 + 0.2)` gives `0.30000000000000004d` and `pp.days(1/3)` gives `0.3333333333333333d`, which then shows up in exports and `str()`. It is also inconsistent: money, percent and `engine.model.hours/days` all refuse floats with a `TypeError`. **Verdict: acceptable convenience, Low risk.** I would tighten it by accepting a float only when its `repr` has at most 6 significant decimal places (or when `float(Decimal(repr(x))) == x` and `len(repr(x)) <= 10`), and otherwise raising `TypeError` with the "pass a str" hint.

## 4. Efficiency recommendations

Ordered by expected impact on interactive use (10k-task figures from my measurements, same generator as `docs/performance.md`).

1. **Staleness by counters instead of hashing (finding 7).** Today the first read after every edit spends about 176 ms on `schedule_fp + cost_fp`. Keep `schedule_rev` / `cost_rev` counters, bumped in `_commit` according to the operation (edit methods already pass `refresh=True` for cost-only edits). Store them with each run and compare integers in `state()`. Compute fingerprints only at save/load/import time, or keep them for CSV/DB portability. As a quick win, `cost_fp = sha256(schedule_fp + rates)` halves the cost. **Impact: about 190 ms less per edit at 10k (about 1 s at 50k); real per-edit latency drops from about 230 ms to about 40 ms.**
2. **Cheap recost (finding 8).** Compute one fingerprint per edit, compute costs once per `schedule_fp` (durations are identical across dependency-only, preview and leveled), `UPDATE` only the cost columns, and drop the deep `!=`. **Impact: rate / unit / days-per-year edits go from 2.3–3 s to roughly 0.3–0.5 s at 10k.**
3. **O(changed) project edits.** Each edit runs `dataclasses.replace(Project)`, which goes through `__post_init__`: it re-sorts and re-type-checks all four collections and rebuilds the whole `_ProjectIndex`. That costs 33–37 ms at 10k and 0.8 s at 50k. Options:
   - (a) A private `Project._evolve(changes)` that trusts the already-sorted tuples, updates the index incrementally for the single changed object (bisect insert in the sorted tuple, patch the per-key dicts), and skips the type checks of untouched collections.
   - (b) A persistent structure (dict-backed collections with lazily materialized sorted tuples).
   (a) keeps the public model unchanged. **Impact: 10–50 times faster per edit (about 1–3 ms at 10k), and it keeps 50k interactive.**
4. **Validate once per compute.** `level_preview` with a stale base runs `validate` and `forward_pass` twice (`schedule`, then `level` builds a new `_Prepared`). `validate` plus `topological_order` run Tarjan SCC three times per pass (parent graph, dependency graph, then `topological_order` checks for cycles again). Pass `_Prepared` from `schedule` into `level` when the fingerprints match. Give `topological_order` an `assume_acyclic=True` path after validation; Kahn's algorithm already detects leftover nodes. **Impact: about 0.1–0.2 s off `level_preview` at 10k; about 70 ms off each `schedule` from the repeated SCC passes.**
5. **Result assembly.** Per `docs/performance.md`, `_assemble` is about 63% of `schedule` time, and `ScheduleResult.__init__` alone is 0.5 s under profiling. The likely causes are the frozen-dataclass `__setattr__` path and the materialization of `node_results` / `assignment_results` CSV views up front. Build the CSV views lazily (on export), and compute fingerprints once per `_Prepared` (`schedule_fp` is recomputed in `_assemble` even though `level` just checked it). **Impact: roughly 30–40% of `schedule` / `level` wall time.**
6. **CSV.** Export: replace the per-character `any(ch in cell ...)` in `_quote` with a precompiled `re.compile(r'[,"\r\n]').search`, or with `csv.writer(lineterminator="\n", quoting=QUOTE_MINIMAL)`, which gives the same RFC 4180 output. **Impact: export about 1.5 s down to about 0.4 s at 10k.** Import: the pure-Python `_tokenize` (1.9 s under profile) can be replaced by `csv.reader(io.StringIO(text), strict=False)`. Line numbers can be kept with `reader.line_num` (it counts physical lines, which handles quoted newlines). Do `_trim` and `_check_columns` only on the columns each record type uses. **Impact: import about 2.1 s down to under 1 s at 10k.**
7. **`load`** reads the saved project fully (`repo.load_project(conn, pk).name`) only to get its name, then copies it, then `reload` reads it again. Read `project_name` from the `projects` row instead. **Impact: about 1/3 of `load` (about 0.3 s at 10k).**

## 5. Things done well

- **Exact arithmetic where it matters.** `TimeQty.to_minutes` uses `as_integer_ratio` with ceiling floor-division, sizing uses `Fraction`, and capacity sums are exact and order-independent. No float appears anywhere in the engine's time or money paths. The only floats are progress fractions and the deliberate facade conversion.
- **Leveling.** The implementation is compact and readable, with a correct termination argument: the step function's last step is 0 and each fit is monotone. Ties are broken deterministically by (dependency start, WBS rank, id). Over-capacity "forced" tasks are explained in `UnresolvedOverload`.
- **Calendar axis.** The lazy, bisect-based working-day list and the explicit `start` / `finish` boundary conventions are a clean answer to D7. `to_axis` rounds sub-minute times up, so it never under-reports.
- **Transactions.** Single-connection edits are atomic and the cache is swapped only after commit. Re-entrant savepoints are used, and `IntegrityError` is mapped to `Conflict`. Import parses fully before touching the DB, so a failed import leaves the workspace unchanged, as tested.
- **Jobs.** Results are delivered only on the owner thread, and cancellation and delivery are guarded by the same lock. Late and overtaken results are handled through fingerprints rather than flags. Results that only miss a rate change are recosted on arrival. Inline, thread and spawn-process executors all work (verified: late-job rejection, process-pool cancel, rejection after import).
- **Determinism.** All set and dict iteration feeding outputs or fingerprints is sorted. Canonical JSON with normalized numbers is used for fingerprints.
- **Hygiene.** Tests are strong (1042 passing, property tests across modules, executed notebook), and ruff and mypy are clean.
